## 2. Worklet 与音频链路

| 项目 | 结果 | 解读 |
|---|---|---|
| 采样率 / 声道 | 48000 Hz / 2 ch | 正常 |

| 总上报延迟 | 98 ms | 按当前阈值属于“偏大” |

| 心跳 | 5921 次 / 600 s ≈ 9.87 次/s | 接近设计的 10 Hz，音频线程持续运行 |
| 心跳最大间隔 | 151.7 ms | 见下文的解释 |

**关于 151.7 ms 心跳间隔：** 这是主线程收到 `postMessage` 的间隔，不等于音频线程真的丢了 151.7 ms。若音频线程发生硬 dropout，听感上通常会有明显断音，但本次用户标记为 0。更可能的解释是主线程短暂卡顿（同一时间段 FPS 最低到 35.6），导致心跳消息延迟。P1 可以再加一个基于 Worklet `currentFrame` 连续性的硬指标来区分“消息延迟”和“音频丢帧”。

### 切后台表现

测试期间页面多次隐藏，累计约 4.6 分钟处于后台：

- `visibility hidden` 的时间段包括约 26 s、96 s、153 s；
- 音频线程没有停：600 s 内仍有 5921 次心跳，结束时 `audioState = running`；
- 主线程 `requestAnimationFrame` 在后台暂停，所以 FPS 样本只有 320 个（约等于可见时间），不是 600 个；
- `longFrames = 0`，说明没有可见状态下的 >2 s 主线程冻结；
- 最低 35.6 fps 是可见期间某个 1 秒窗口的真实低值，可能与页面显示/隐藏或重排有关，但没有造成音频标记。

这是一个很强的正向结果：**车机在页面后台时仍然保持音频运行，且没有音频焦点状态变化。** 但本次没有主动播放导航播报或语音助手提示，音频焦点“被抢占”的场景还需要单独测。

## 6. 98 ms 延迟怎么决策

这是目前唯一可能影响产品形态的指标。

**选项 A：接受 98 ms，进入 P1。**
适合“连续行驶声浪”：发动机转速本身有惯性，P1 可以用虚拟驾驶模型让 RPM 平滑变化，98 ms 会被发动机惯性/涡轮感部分掩盖。踩下油门到声音变化仍会略慢，但不会像打击乐那样明显。

**选项 B：要求更低的踏板响应，走原生/OEM。**
浏览器无法控制车机 Audio HAL 的 80–88 ms 输出缓冲；`latencyHint: 'interactive'` 已经用了，Worklet 也不会降低这部分。若目标是把延迟压到 20–30 ms，Web 方案大概率不够，需要原生 AAudio/OpenSL 或车机音频接口。

**选项 C：接受延迟，但做交互设计上的补偿。**
- 以“自动演示 / 虚拟驾驶”为主，减少瞬时踏板触发；
- 视觉转速表与音频输出对齐（用 `outputLatency` 做补偿），让画面和声音一致；
- 把“轰油门”设计成有预兆的转速爬升，而不是瞬时脉冲。

在决定之前，请先用节拍器做一次主观判断：**如果 98 ms 听起来只是“有一点晚”，P1 可以做；如果明显不跟手，就要认真考虑原生方案。**
